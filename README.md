# kebbie-hub

A hub that lets you follow and steer [kebbie](https://github.com/gronare/kebbie) from your phone. Each machine running kebbie dials out to the hub; your account reads every machine's board in the web app, get notified when a task needs you, and answer questions, approve pushes or start tasks.

The hub is a mailbox, never a party. Boards are end-to-end encrypted from a machine to the account that connected it, and only that account's passkeys unlock the key that opens them. Commands are signed by a device the machine trusts. The hub sees who talks to whom and when, not what is said, and it cannot start anything on a machine.

This repository holds:

- `kebbie-hub-protocol`: envelopes, messages, account keys and pairing, error reports, error signals and their proof of work, plus the test vectors other implementations are checked against.
- `kebbie-hub`: the hub server. It relays sealed boards from machines to the account that owns them, signed commands from devices to machines and sealed results back, pushes sealed notices to devices through Web Push, and carries pairing between them. It keeps each account's passkey-wrapped key without being able to open it. It also takes error reports and error signals from kebbie installs for kebbie's maintainers.
- `kebbie-hub-api`: the request and response bodies of the hub's HTTP API.
- `kebbie-hub-fakes`: `fake-machine` and `fake-phone`, two CLIs that stand in for kebbie and for a device that sends commands. The fake machine never runs anything: it prints what kebbie would do.

## The protocol

- **Envelope.** A plaintext header (`v`, `id`, `kind`, `from`, `machine`, `at`, `exp`, `schema`, `kc`, and for notices `urgency` and `collapse`), one key row per recipient, the ciphertext and a signature. Each kind has a maximum lifetime (commands 24 hours, notices 1 day, results 7 days, boards 1 day); a header with a longer one is refused.
- **Content.** AES-256-GCM with a fresh 32-byte key and 96-bit nonce per envelope; the header's canonical bytes are the associated data. `kc` is SHA-256 of the content key, so a recipient handed a different key detects it before decrypting.
- **Key rows.** The content key is sealed to each recipient (an account, a device or a machine) with HPKE (RFC 9180) base mode, `DHKEM(X25519, HKDF-SHA256)`, `HKDF-SHA256`, `AES-128-GCM`, with the header bytes as associated data. A row copied under another recipient's id does not open, because it is sealed to the first recipient's key.
- **Signature.** Ed25519 over the header bytes followed by the ciphertext. Key rows are outside it, so the hub can hand each device only its own row.
- **Commands.** `authorize` drops, without any reply, anything that fails before the signature is verified: wrong version or shape, not a command, another machine, an unknown device, a bad signature. A validly signed command whose id the machine already applied for that device gets the stored result again, even once it has expired. Otherwise the machine applies it only if it is unexpired, from a device with the `control` role, of a kind the machine accepts and well formed, and answers a refusal with a reason the device can show.

The message types (board snapshot, notice, answer, push approval, start task, run routine, result, alert) are in `crates/kebbie-hub-protocol/src`. A board carries only allow-listed fields: no local paths, hostnames, pane ids or terminal titles. A board is sealed to the account's encryption key (key row `acc_…`), and to the machine itself.

## Account keys

The passkey is the key. Each account has one key pair for reading (X25519) and one for signing (Ed25519), made at random in the browser at the account's first sign-in. The private halves reach the hub only wrapped, and the hub cannot unwrap them. `AccountKey` in the protocol crate (`{account, version, keys}`) is the public half, versioned for a later rotation.

- **Salt.** Each passkey has a random 32-byte PRF salt, drawn by the hub when the passkey is made and handed out with every ceremony: `prf_salt` with the creation options, `prf_salts` (credential id to salt) with the request options of a sign-in that names an account or a credential.
- **PRF.** The web app asks WebAuthn's `prf` extension with that salt (`eval.first` when creating, `evalByCredential` when signing in). If `create()` gives no PRF result, it signs in once more with the new passkey before it concludes the device has none. It decides from the results, never from capability flags, and posts `getClientExtensionResults()` nowhere: the hub never sees PRF bytes.
- **Wrap.** The wrapping key is HKDF-SHA256 with the PRF output as input, the salt as salt and `"kebbie-hub account key v1"` as info, 32 bytes. The two private keys (signing then encryption, 64 bytes) are sealed with AES-256-GCM under a fresh 12-byte nonce; the associated data is `"kebbie-hub account key wrap v1"`, the account id and the raw credential id each as a 2-byte big-endian length and its bytes, and the key version as 4 bytes. The wrapped form is nonce followed by ciphertext and tag, 92 bytes. The account key is never derived from the PRF, only wrapped by it.
- **Wrappers.** The hub keeps, per passkey, its salt and the wrapped keys with their version. Several passkeys can each wrap the same keys. Every wrapper is signed by the account's signing key over `"kebbie-hub account key wrapper v1"`, the account id and credential id as above, the version, both public keys and the SHA-256 of the wrapped bytes, so only a browser that has unlocked the account adds one. The first one comes with the keys themselves (`POST /v1/a/key`), later ones from an unlocked session (`PUT /v1/a/passkeys/<id>/wrapper`). The hub refuses to remove the last passkey that unlocks the account.
- **Forks.** The web app remembers, next to the last credential id, the account and the fingerprint of its signing key. When the hub later reports no key for that account it creates none and shows that the key is missing, and when it reports another key it refuses it.
- **Unlocking.** Signing in answers with the passkey that was used, its salt and its wrapper. The web app unwraps in memory, checks that the private keys give the public keys the hub reported, and keeps them as non-extractable `CryptoKey`s for the page's life. Nothing secret is kept in IndexedDB or local storage; the app remembers only the last credential id, so the next unlock is one passkey prompt.
- **Without PRF.** A passkey that gives no PRF output, or one without a wrapper, signs in but cannot unlock: the app says this browser can't unlock the boards, that a device whose passkey can (iCloud Keychain, Google Password Manager, 1Password) works, and offers another passkey. Neither reads a board.
- **Asleep.** A machine whose newest board has expired shows as asleep with the hub's last-seen time, not as an error.
- **Machines.** The account signs one list of the machines it trusts: `"kebbie-hub account machines v1"`, the account id as above, a counter as 8 bytes, the number of machines as 4 bytes, and per machine, in ascending id order, its id as above and its signing and encryption keys (`MachineList` in the protocol crate). The browser that hands a machine the account key adds it to the list, and removing a machine in the web app takes it off before the hub deletes it (`DELETE /v1/a/machines/<id>` answers `409 still-listed` until then). The hub keeps the newest list (`PUT /v1/a/machines`, refused with `409 stale-list` unless its counter is higher, `400 unknown-machine` for a machine not the account's with those keys) and hands it out with the boards. The web app shows a board only from a machine on a list the account signed whose counter is at least the highest it has seen (kept in IndexedDB, not secret), so a hub that swaps a machine's keys, keeps serving a removed machine or replays an older list gets none of its boards read. A machine the hub deleted (`admin remove-machine`) drops off the list the next time an unlocked browser reads the boards: it signs a list without it. A browser that has never seen a list trusts the newest one the hub hands it.
- **Board age.** A board lives at most a day. The web app also remembers, per machine, the highest revision and signed time it has read, and refuses an older board (`rolled-back`). It keeps those marks in IndexedDB and in memory; when the browser cannot store them it says so on the board, and the marks then hold only for that visit. A device that has never read a board, or a private window, has no marks: a hub can show it the second-newest board of a machine for up to a day.
- **Fingerprints.** A machine pins the account's keys by their fingerprints: SHA-256 of `"kebbie-hub account signing key v1"` (or `"kebbie-hub account encryption key v1"`), the account id as above, the version as 4 bytes and the key. `AccountKey::fingerprints` and `accountFingerprints` in `js/protocol.js` compute them; `vectors/accounts.json` has the wrap, its refusals, both signatures, the fingerprints and the handoff below.

## Pairing

A device pairs with a machine to send it commands and receive its notices; boards go to the account instead (see [Connecting a machine](#connecting-a-machine)). Pairing binds both parties' keys without trusting the hub that relays them. The device commits before it learns anything from the machine, so the hub cannot try substitute keys until the two codes match.

1. The device draws a 32-byte nonce `n_d` (from `crypto.getRandomValues`; `pairingNonce()` in `js/protocol.js`) and sends `commitment = SHA-256("kelpie-pair-commit-v1" || D || n_d || code)`, where `D` is its signing key followed by its encryption key and `code` is the one-time code from the hub.
2. The machine draws a fresh 32-byte nonce `n_m` and replies with its keys `M` and `n_m`.
3. The device reveals `D` and `n_d`. The machine refuses the pairing if they do not hash, together with the code the machine holds, to the commitment, so a machine holding a different code fails here before any digits are shown.
4. Both sides show `SHA-256("kelpie-pair-v1" || M || D || n_m || n_d || code)` as six digits. The user confirms that the digits match before the machine adds the device to its trusted list.

The flow holds only if each side takes one chance per attempt:

- One pairing invocation (`kebbie hub pair` on the machine, `fake-phone pair` on a device) accepts exactly one commitment.
- A commitment mismatch, a second commitment or a timeout ends the invocation with a visible failure. The user starts again; nothing retries quietly.
- The device shows every attempt, including failed ones, so an attempt the user did not start is visible.

A hub that swaps keys has to fix its substitutes before it sees `n_d`, so it matches the codes only by a one-in-a-million guess. `DevicePairing` and `MachinePairing` in the crate, and `pairingCommitment` and `machineComparisonCode` in `js/protocol.js`, carry the two sides.

## Connecting a machine

`kebbie hub connect` connects a machine to a hub in one step, in the shape of OAuth's device authorization grant (RFC 8628). Nobody needs a join code or a shell on the hub.

1. The machine posts its public keys and a name to `POST /v1/m/connect` and gets a `device_code` (its secret for polling), a `user_code` like `K7QF-M2XD`, `verification_uri` and `verification_uri_complete` (`<origin>/connect?code=K7QF-M2XD`), `interval` and `expires_in`.
2. The machine draws a 32-byte secret of its own and opens `verification_uri_complete#k=<secret>&m=<fingerprint>` in the browser, where the fingerprint is `SHA-256("kelpie-connect-machine-v1" || M)` over its signing and encryption keys. A browser never sends the part after `#` to the hub. `ConnectSecret` in the protocol crate and `parseConnectFragment` and `machineFingerprint` in `js/protocol.js` carry it.
3. The page shows the machine's name and the user code. A browser that is not signed in creates a passkey there (on an open hub; see [Accounts](#accounts-and-who-holds-what)) or signs in with one, then the person checks the code against the terminal and presses Connect. Connect needs a session that a passkey signed in within the last 5 minutes (`401 reauth-required` otherwise, and the page asks for the passkey again) and the hub's `Origin`. The machine belongs to the account that approved it. Cancel denies it.
4. The machine polls `POST /v1/m/connect/token` every `interval` seconds and gets its machine id and a `khm_` token, the same token a join code gives.

**Handing over the account key.** A browser that came by the link and has unlocked the account sends, with the approval, a commitment to the account key: `SHA-256("kebbie-connect-account-commit-v1" || account || version || signing key || encryption key || n_b || secret)`, with the account id as a 2-byte length and its bytes and the version as 4 bytes, `n_b` a fresh 32-byte nonce and the secret the fragment's `k` (`AccountHandoff` in the protocol crate, `accountCommitment` in `js/protocol.js`). The hub opens a pairing that starts committed, and the token answer names it. The machine replies `M` and `n_m` as in any pairing; the browser checks that `M` hashes to the fingerprint in the fragment before it reveals `{key, nonce}` (`POST /v1/a/pairings/<id>/reveal`), and the machine checks the reveal against the commitment and its secret (`pin_account`) before it pins the account's fingerprints and admits. Then the browser signs a new machine list with the machine on it. No digits are compared: the user code on both screens tells the person they approve the machine in front of them, and the secret and the fingerprint, carried past the hub in the fragment, bind both keys. A hub that commits keys of its own fails the machine's check, since it never saw the secret, and one that hands the browser other machine keys fails the browser's. The hub also refuses a reveal of any key but the account's own (`409 keys-differ`). A browser that reached the page by a typed code has no fragment; it connects the machine without the handoff, and the board stays unreadable until the machine is connected from the link.

The codes:

- A user code is 8 symbols from `0`-`9` and `A`-`Z` without `I`, `L`, `O` and `U`, so it reads aloud and survives a mistyped `O` or `I`. Both codes are valid 10 minutes and once, and the hub keeps only their SHA-256 hashes.
- The token endpoint answers `400` with RFC 8628's error names: `authorization_pending`, `slow_down` (polled sooner than `interval`; the interval grows by 5 seconds), `access_denied` (once; the code is gone after that), `expired_token`, and `invalid_grant` for a code it does not know or already redeemed.
- Starting a connect is limited per address (10 at once, 10 a minute), looking up and approving codes per account (10 at once, 10 a minute).
- An approval that is never redeemed leaves nothing: the machine it named is deleted with the expired code.

`kebbie-hub admin join-code` keeps working for scripts; a machine that joined with one belongs to no account.

## Plans

The hub knows whether each account's plan is `active` or `inactive`, with an optional `until`; subscriptions themselves live in a separate billing service. `--plans off` (the default, for a hub you run for yourself) makes every account entitled. With `--plans on`:

- approving a connect, and every call a machine makes to post or read (board, notice, inbox, results, pairings), needs an entitled plan on the account the machine belongs to: `active` with no `until` or one still ahead. Otherwise the answer is `402` with `{"error": "plan-inactive", "url": <--billing-url>}`, for kebbie to show "Start a subscription at <url>".
- signing in, the account page and removing devices keep working. `GET /v1/a/account` carries the plan and, when it is not entitled, `billing_url`.
- the owner is always entitled, and machines that joined with a join code (no account) are not gated.
- an account created after the upgrade to schema 7 starts `inactive` until the billing service sets it; accounts carried over from an older schema start `active`.

The billing service uses an admin token with the `billing` scope (`kebbie-hub admin token --name billing --scope billing`): `GET /v1/admin/accounts?email=<address>` finds an account by its verified email (only accounts carried over from a hub that had email sign-up have one), and `PUT /v1/admin/accounts/<id>/plan` with `{status, until?}` sets the plan. Both answer `{account, handle, email, plan: {status, until, entitled}}`. The same token lists the accounts, reads one for support, and deactivates and activates an account: one scope covers what the billing service and its support pages do, and none of these answers carries an email or anything of a board. A token of the other scope gets `403 wrong-scope`.

## Running a hub locally

Start the dev hub with `bin/dev`: it builds the hub and runs it with `--dev --signup open` at `http://localhost:8470`, keeping its data in `~/.local/state/kebbie-hub-dev` across restarts (`PORT=<port>` moves it, `Ctrl-C` stops it, `bin/dev reset` wipes the data). Point kebbie at it with `KEBBIE_HUB_DEV=1 kebbie hub connect`. Safari works on `http://localhost`. With `KEBBIE_HUB_GITHUB_CLIENT_ID` and `KEBBIE_HUB_GITHUB_CLIENT_SECRET` set to a GitHub OAuth App whose callback is `http://localhost:8470/auth/github/callback`, it offers GitHub sign-in too.

```sh
cargo build --workspace
target/debug/kebbie-hub --dev
```

The hub links OpenSSL (through `webauthn-rs`) built from source and statically, so the binary needs no system OpenSSL; building it needs a C compiler, `make` and `perl`.

`--dev` listens on `127.0.0.1:8470`, keeps its sqlite file in `kebbie-hub-dev` under the system temp directory, uses `localhost` as the passkey relying party with `http://localhost:8470` as the origin, signs push requests with this repository's URL as the VAPID subject, and lets a pairing code create a device without an account so the fake phone can pair for commands. `--data <dir>`, `--listen <address>`, `--rp-id <domain>`, `--origin <url>` and `--vapid-subject <contact>` override these; without `--dev` all five are required and the origin must be `https://`, and with `--dev` the hub refuses to listen on anything but a loopback address and takes a plain `http://` origin only on `localhost` or a loopback address.

The VAPID subject is the contact every push service sees in the hub's push requests: `mailto:you@your-domain` or the hub's `https:` URL. The hub refuses to start with anything else, including a `localhost`, `.local`, `.test`, `.internal` or IP address, because Apple answers such tokens with `403 BadJwtToken`. The hub's VAPID key pair is made on first start and kept in `vapid.key` in the data directory (mode 0600, the P-256 private scalar as base64url); `--vapid-key <file>` keeps it elsewhere. The hub refuses to start when the key file is readable by group or others. The push services are reached over TLS with the platform's root certificates, so a container image needs its CA bundle (`ca-certificates` on Debian or Alpine) for real pushes. Keep the file across restarts and moves: a new key invalidates every device's push subscription, and the web app has to subscribe again. `--push-allow-host <host>` (repeatable, `*.example.com` for subdomains) accepts push endpoints on a host beyond the known push services, for a self-hosted push service or tests; on a loopback host it may be plain `http:`. Behind Cloudflare, `--trusted-proxy cloudflare` takes the client address from `CF-Connecting-IP`; without it the hub uses the TCP peer and ignores that header.

A public hub:

```sh
kebbie-hub --data /var/lib/kebbie-hub --listen 0.0.0.0:8470 \
  --rp-id hub.example.com --origin https://hub.example.com --trusted-proxy cloudflare \
  --vapid-subject mailto:you@example.com
kebbie-hub --data /var/lib/kebbie-hub admin invite
```

On its first start with no accounts, the hub prints a one-time setup link (`<origin>/setup?token=kho_…`) to its log; whoever opens it creates a passkey and becomes the hub's owner. Without the link nobody can claim a fresh hub. Each start mints a new link while no account exists, and the previous one stops working.

`--signup invite` (the default) lets people in by invite only: from `admin invite`, or as a link the owner makes in the admin page. `--signup open` also lets anyone whose machine opened a connect link create an account there with a passkey. The hub sends no mail. `--plans on` and `--billing-url <url>` turn on [plans](#plans).

`GET /healthz` answers `204` without credentials, for a load balancer's or Kubernetes' probes. `SIGTERM` and `Ctrl-C` both stop the hub, giving open requests 5 seconds to finish.

Error reports and signals arrive at `/v1/reports` and `/v1/signals` without credentials, so in front of a public hub a WAF rate-limit rule on those paths (Cloudflare's rate limiting rules, for one) is recommended on top of the hub's own limits. `--report-difficulty <bits>` sets the proof of work for both (20 by default, about a second on a laptop).

Upgrading a live hub from schema 9 to 10 (the release that records how each account was made) goes the same way as below, with the backup named `hub-v9.sqlite3`; the new binary adds the column for the ticket an account was made with at start-up. Accounts made before keep it empty.

Upgrading a live hub from schema 8 to 9 (the release that adds GitHub sign-in) goes the same way as below, with the backup named `hub-v8.sqlite3`; the new binary adds the column for an account's GitHub login at start-up and keeps everything there.

Upgrading a live hub from schema 7 to 8 (the release that adds account keys) goes the same way as below, with the backup named `hub-v7.sqlite3`; the new binary adds the account key and wrapper tables, a PRF salt for every existing passkey and the machine signature and handoff columns at start-up. Boards stored before are still sealed to devices, and machines connected before are on no signed list: the web app shows them as not confirmed until each machine is connected again from its link.

Upgrading a live hub from schema 6 to 7 (the release that adds connecting, owners, sign-up by email and plans) goes the same way as below, with the backup named `hub-v6.sqlite3`; the new binary adds the connect table and the account, machine, invite and admin token columns at start-up and keeps everything there. Existing accounts keep an `active` plan, existing admin tokens have the `reports` scope, and existing machines belong to no account. The oldest account becomes the owner and the rest are members; this happens once, during that upgrade. To make another account the owner, run `kebbie-hub admin owner <account id> --replace`.

Upgrading a live hub from schema 5 to 6 (the release that adds error signals) goes the same way as below, with the backup named `hub-v5.sqlite3`; the new binary adds the signal tables at start-up and keeps every report, key standing and token. A schema 4 database gains both releases' tables at once.

Upgrading a live hub from schema 4 to 5 (the release that adds error reports): stop the hub, back up its database with `sqlite3 hub.sqlite3 ".backup hub-v4.sqlite3"` in the data directory, then start the new binary, which adds the report tables at start-up. To roll back, stop it, restore `hub-v4.sqlite3` as `hub.sqlite3` and start the old binary. Never run the new binary's `admin` commands against a database an old hub still serves: they upgrade it under the running hub.

`admin invite` mints a one-time sign-up code, valid 7 days. `admin machines` lists the machines that joined, and `admin remove-machine <id>` removes one with its board, queue and admissions; its token stops working at once. `admin accounts` lists the accounts by id (`acc_…`) with their role, machines and last-seen time. `admin owner <account id>` makes that account the owner, for a hub whose owner account is lost or should change hands. A hub has one owner: while another account is the owner the command changes nothing and says so, and `--replace` demotes that account to member in the same step. A deactivated account cannot become the owner. The change is in the event log as `account.owner`.

In a second terminal, mint a join code and join a machine:

```sh
target/debug/kebbie-hub admin join-code --dev
target/debug/fake-machine --state machine.json join http://127.0.0.1:8470 <join code> --name mac
```

A board is read in the web app by the account that connected the machine. To see one, sign up at `http://localhost:8470` in any browser, connect a fake machine and post a board:

```sh
target/debug/fake-machine --state machine.json connect http://127.0.0.1:8470 --name mac
target/debug/fake-machine --state machine.json post-board examples/board.json
```

`connect` prints a link; open it in the signed-in browser and press Connect. The machine pins the account's key and seals every later board to it.

Pair a phone for commands. The machine prints a pairing code and waits; the phone takes the code, and both print six digits. Answer `y` on the machine only when they match:

```sh
target/debug/fake-machine --state machine.json pair
target/debug/fake-phone --state phone.json init http://127.0.0.1:8470
target/debug/fake-phone --state phone.json pair <pairing code>
```

Send a command from the phone and apply it on the machine. The phone waits for the result and prints it; `push` approves the head `--head` names:

```sh
target/debug/fake-machine --state machine.json apply
target/debug/fake-phone --state phone.json answer refunds@greenhouse 1761069540-4411-0-question --choice 1
target/debug/fake-phone --state phone.json push refunds@greenhouse --head 9f3c2a1e5b7d4c6a8b0e2f4d6c8a0b2e4f6d8c0a
target/debug/fake-phone --state phone.json start greenhouse invoice-rounding "Fix the rounding in invoices"
target/debug/fake-phone --state phone.json routine nightly-deps
```

Post a notice. The machine seals it to every device it paired with; the hub pushes each subscribed device its own cut of the envelope:

```sh
target/debug/fake-phone --state phone.json push-subscribe --endpoint <push endpoint> --keys
target/debug/fake-machine --state machine.json notice "Keep the old endpoint for a release?" \
  --event question --urgency high --collapse refunds@greenhouse
target/debug/fake-machine --state machine.json notice "answered" --collapse refunds@greenhouse --retract
```

`push-subscribe` makes fresh subscription keys, keeps the private half in the state file and registers the endpoint; `--keys` prints the subscription it sent. A command-line phone has no push service of its own, so the endpoint is one the hub accepts (a known push service, or a host given with `--push-allow-host`). `--collapse` takes the task's `task@repo`: the fake machine turns it into an opaque tag (a SHA-256 over its own key and `event:address`; kebbie will use an HMAC key shared at pairing), so the next notice for that task replaces this one. `--retract` sends a notice whose `retract` names that tag, for the app to close the earlier one.

`fake-machine apply` runs until stopped (`--once` polls once); it keeps the ids it applied, with their results, in its state file. `fake-machine role <device> read` makes a device read-only, so its commands are refused with `not-allowed`. `fake-machine poll` long-polls the machine's queue once, and `fake-phone attempts` lists every pairing attempt, failed ones included. Both CLIs keep their keys and tokens in the `--state` file, written with mode 0600. Against a hub without `--dev`, give the phone a device an account registered: `fake-phone init <hub> --device <id> --token <token>`.

## Sign in with GitHub

A hub can let people sign in and sign up with GitHub beside passkeys. It is off until the hub has a GitHub OAuth app:

1. On GitHub, open Settings → Developer settings → OAuth Apps → New OAuth App (or the same under an organization). Set the homepage URL to the hub's origin and the authorization callback URL to `<origin>/auth/github/callback`, like `https://hub.example.com/auth/github/callback`. A local hub needs an app of its own, with `http://localhost:8470/auth/github/callback`.
2. Generate a client secret.
3. Start the hub with the client id as a flag and the secret in the environment, never on the command line:

```sh
KEBBIE_HUB_GITHUB_CLIENT_SECRET=<client secret> kebbie-hub --data /var/lib/kebbie-hub ... \
  --github-client-id <client id>
```

The hub refuses to start with a client id and no secret. It never logs the secret, never stores it and never sends it anywhere but GitHub's token endpoint. `--github-web-url` and `--github-api-url` point it at another GitHub (`https://github.com` and `https://api.github.com` by default), for GitHub Enterprise Server or a test double; plain `http://` is taken only on a loopback address.

`GET /auth/github` starts the OAuth web flow: it sends the browser to GitHub with a fresh `state`, a PKCE challenge (S256) and the scope `read:user`, and sets the state cookie (`__Host-kebbie_github`, or `kebbie_github` on a plain `http://` hub), `HttpOnly`, `SameSite=Lax` so it rides along on GitHub's redirect back, valid 5 minutes. `GET /auth/github/callback` takes the state once, checks the cookie against it before it trades the code, reads the GitHub user's id and login, and sends the browser back to `next` (a path on the hub, `/` otherwise). An account holding that GitHub id gets a session. Otherwise the ticket the sign-in started with makes an account, by the same rules as a passkey sign-up (see [Accounts and who holds what](#accounts-and-who-holds-what)); without one, the browser comes back with `github_error=no-account`. Refusals come back the same way: `expired` (an unknown, spent or foreign state), `denied` (cancelled on GitHub), `failed`, `signup-closed`, `unauthorized` (a used or expired ticket), `github-taken`, `signed-out` and `deactivated`. Both routes are limited per address like the other calls without credentials. The access token is used for the one `GET /user` and then dropped.

## Accounts and who holds what

People sign in to the hub with its own accounts. An account holds passkeys (WebAuthn, user verification required), its key wrapped by each passkey that can unlock it (see [Account keys](#account-keys)) and the devices it registered. The hub never reads a board, because boards are sealed to the account key it holds only wrapped.

- **Sign-up** takes one ticket, then registers the first passkey: the setup token of a fresh hub (`setup`, which makes the owner and works only while there is no account), an invite (`invite`, from `kebbie-hub admin invite` or an invite link), or on an open hub the user code of a pending connect (`connect`, from the link `kebbie hub connect` opens; one account per code, and the account then approves that connect like any other). No account has a name: the hub makes up an internal handle for each (`k` and 12 hex digits), which no page shows and no call or command takes; accounts are named by their id (`acc_…`). The ticket is spent when the passkey is accepted, so two ceremonies started with one make one account. A hub with [GitHub sign-in](#sign-in-with-github) also signs up with GitHub in place of the first passkey, on the same tickets and the same rules; GitHub never makes an account without one.
- **GitHub** signs in the account that holds the GitHub user's id, with the same session cookie a passkey gets. The hub keeps the id and the login (shown to the account only) and asks GitHub for nothing else; it never reads or stores an email. GitHub cannot unlock the account key, so after a GitHub sign-in on an account without a key the web app asks for a passkey ("Add a passkey to unlock your boards"), and that passkey makes the key and wraps it, as the first passkey of a passkey sign-up does; a connect waiting on the page then hands the machine the key. "Not now" leaves the browser signed in and unable to read a board, and says so. An account that has a key unlocks with one of its passkeys as before. A signed-in account links GitHub on its account page, `/account` (`GET /auth/github?link=1`), and removes it there (`DELETE /v1/a/github`); a GitHub user another account holds is refused (`github-taken`), and GitHub stays while the account has no passkey (`409 last-sign-in`).
- **The owner** is the account made from the setup link, or the one `kebbie-hub admin owner <account id>` names. Only the owner opens `/admin` and the `/v1/a/admin/` endpoints (`403 not-owner` for anyone else): counts of accounts, machines, devices, reports and signals; accounts with their plan, machines, devices and when they were last seen; invite links; deactivating and activating an account; removing a machine; allowing, blocking and acknowledging error reports; error signal counts. Deactivating an account, removing a machine and blocking a report key need a session signed in, by passkey or GitHub, within 5 minutes (`401 reauth-required`, and the page asks for the passkey again); reading, inviting, activating, allowing and acknowledging do not. A deactivated account's sessions are deleted, it cannot log in, and its devices' and machines' tokens are refused until it is activated again, and its devices' open event feeds end. The owner cannot be deactivated (`409 owner-stays`).
- **Passkeys are discoverable.** Sign-up and adding a passkey ask for a resident credential with user verification (`residentKey: "required"`), so the authenticator itself offers the account.
- **Signing in** names no account: `POST /v1/a/login/begin` with `{}` returns request options with no `allowCredentials`, the authenticator offers its passkey for the hub, and the hub finds the account from the credential's user handle and accepts only that account's passkeys. The web app has one "Sign in with passkey" button and, where the browser supports it, starts a conditional request so the passkey shows in autofill; the request options carry no `mediation`, so the page picks a button or autofill. A passkey made before passkeys were discoverable can no longer sign in; add a new one from a device that still has a session. The hub keeps each passkey's signature counter and refuses a login whose counter does not move past it (unless both are zero), as a sign the passkey was cloned; a user handle no account holds gets `401 unknown-passkey`.
- **The session** is an opaque `khs_` token in the cookie `__Host-kebbie_session` with `HttpOnly`, `Secure`, `SameSite=Strict` and `Path=/`, valid 14 days. A hub on a plain `http://` origin, which only `--dev` on a loopback address allows, names it `kebbie_session` without `Secure`, so every browser, Safari included, signs in to it; each hub reads only its own name. The hub stores its SHA-256 hash. Logging out deletes it.
- **Cross-site requests.** Every state-changing `/v1/a/` call needs an `Origin` header equal to `--origin`, or gets `403 cross-origin`. The cookie is accepted on `/v1/a/` only.
- **Reading boards.** The web app reads its account's boards with the session (`GET /v1/a/boards`, and `GET /v1/a/events` for changes); it registers no device. Both are reads, and the cookie is `SameSite=Strict`.
- **Devices.** A logged-in account registers a device and gets its `khd_` token once; a device pairs with machines to send commands and receive notices (the fake phone is one). Every `/v1/d/` call, the event feed included (read with `fetch`, since `EventSource` cannot send a bearer token), takes that token as a bearer token and never the cookie, so no device call rides on an ambient credential and none needs a CSRF check. Logging out leaves the device working; removing the device ends it.
- **Removal.** A machine removes a device it admitted, and the hub stops relaying that device's commands and notices for the machine. An account removes its own devices, which deletes their tokens and ends their event feeds. An admin removes a machine, and the account's feed announces it.

Ceremony state (the challenge a passkey must sign) is kept on the hub for 5 minutes and used once; it never reaches the browser.

## The hub's API

Every endpoint is under `/v1`, apart from the two browser routes of [GitHub sign-in](#sign-in-with-github), `GET /auth/github` and `GET /auth/github/callback`. Admin endpoints (`/v1/admin/`) take a `kha_` bearer token from `kebbie-hub admin token --name <name>`, with the `reports` scope (the default) for the report endpoints and the `billing` scope (`--scope billing`) for the account endpoints. Machine endpoints (`/v1/m/`) take a `khm_` bearer token, except joining and connecting, where the join code or device code is the credential. Account endpoints marked *owner* need the owner's session, and *fresh* a session signed in, by passkey or GitHub, within 5 minutes. Device endpoints (`/v1/d/`) take a `khd_` bearer token. Account endpoints (`/v1/a/`) take the session cookie, except signing up and logging in.

## Error reports

kebbie keeps the problems it meets as local issues. When kebbie or its lead files one of kind `bug`, the board shows it with the exact text that would go out, and asks the user whether to send it to kebbie's maintainers; only the user's yes sends it. The report is plain text, not sealed: it is meant for the people who run the hub.

- **What a report holds.** `title`, `text`, `version` and `os` (`BugReport` in the protocol crate). kebbie redacts paths under the home directory to `~`, repository names, remote URLs and anything shaped like a token before the user sees it. The hub refuses a title that is empty, longer than 200 characters or holds a control character (`400 bad-title`), a `version` or `os` that is empty or longer than 64 characters (`400 bad-field`), and a text over 12 KiB or a body over 16 KiB (`413 too-large`).
- **The install key.** Each install makes an Ed25519 key on its first report. The key is the sender's id. It signs `"kelpie-report-sign-v1" || nonce || SHA-256(report bytes)`, where the report bytes are `"kelpie-report-v1"` followed by each of the four fields as a 4-byte big-endian length and its UTF-8 bytes.
- **Proof of work.** `GET /v1/reports/challenge` hands out `{nonce, difficulty, expires, tag}`: a fresh 32-byte nonce, the difficulty in bits, an expiry 10 minutes out and an HMAC-SHA256 tag over the three under a key the hub draws at start, so a client cannot lower the difficulty or extend the expiry. The sender looks for a `counter` such that `SHA-256("kelpie-report-pow-v1" || nonce || SHA-256(report bytes) || counter as 8 bytes big-endian)` starts with `difficulty` zero bits. `vectors/reports.json` has a worked case.
- **What the hub checks.** In order: the per-address rate (20 at once, 4 a minute; `429 rate-limited`), the tag (`400 bad-challenge`), the expiry (`400 expired-challenge`), the report's size and shape, the work (`400 insufficient-work`), the signature (`400 bad-signature`), the per-key rate (5 at once, 1 a minute) and that the challenge was not used before (`409 challenge-used`). A challenge is spent by the first report that passes, so a hub restart only ends the challenges handed out before it.
- **Quarantine.** A report from a key the hub has not seen waits in quarantine; at most 20 per key and 10 000 in all do, and further ones are dropped, answered like any other. The operator lets a key through with `admin reports allow <key>`, which releases the ones it has waiting, or drops it with `admin reports block <key>`. A blocked key's reports get the same `202` and an id from the same sequence as any other, and are not kept, so a sender cannot tell it was blocked.
- **Reading them.** `admin reports` lists the allowed reports not yet acknowledged, `--quarantine` the waiting ones, `--json` either as JSON; `admin reports ack <id>` marks one handled. `admin token --name <name>` mints a `kha_` token for a maintainer's machine, shown once and kept as a hash under that name; `admin token list` lists the names with when each was made and last used, and `admin token revoke <name>` ends one at once. The token is for `GET /v1/admin/reports` and `POST /v1/admin/reports/<id>/ack`. kebbie on that machine files each allowed report as a local issue of its own and acknowledges it.

Acknowledged reports and those still in quarantine are deleted 30 days after they arrived.

## Error signals

kebbie also counts its own failures, a panic, an internal error or a state file of its own it cannot read, and sends the counts at most once a day, on unless the user turned them off. A signal carries no text.

- **What a signal holds.** `ErrorSignals` in the protocol crate: `version`, an optional `commit`, `os`, `arch`, and `counts`, a list of `{component, kind, count}`. Every text field is a `Name`: 1 to 48 of lowercase ASCII letters, digits and `.` `_` `+` `-`, starting and ending with a letter or digit, so no sentence, path, quote or capital fits. `kind` is one of `panic`, `internal-error` and `corrupt-state`. The hub refuses an unknown field at any level, a value that is not a `Name` and an unknown kind with `422`, and no counts (`400 no-signals`), more than 64 (`400 too-many-signals`), a count of 0 or over 10 000 (`400 bad-count`), a component and kind twice (`400 repeated-signal`) and a commit that is not up to 40 hex digits (`400 bad-commit`).
- **Signing and work.** The same install key and challenge as a report. The signal bytes are `"kelpie-signal-v1"`, then `version`, `commit` (empty when absent), `os` and `arch` each as a 4-byte big-endian length and its bytes, the number of counts as 4 bytes, and per count its `component` and `kind` the same way and the count as 4 bytes. The key signs `"kelpie-signal-sign-v1" || nonce || SHA-256(signal bytes)`, and the work is the report's over that digest. A challenge is spent by whichever report or signal passes first. The difficulty is the report's: a sender spends about a second once a day, in the background.
- **What the hub checks.** The report's checks, in the same order, with the shape above in place of a report's.
- **What it keeps.** Counts per day, version, commit, OS, architecture, component and kind, and whether the sender's key is allowed; never the key with a count. A key the operator allowed for reports (`admin reports allow`) counts as vetted, any other as unvetted, and a blocked key's signals are dropped, answered with the same `202`. To bound one sender, the hub keeps each key's number of batches for the current day, and forgets it when the day turns (UTC): a key sends at most 4 a day. An address (an IPv4 address, or an IPv6 /64) sends at most 200 batches a day, whatever keys it uses, enough for an office or a carrier NAT full of installs; that count lives in memory only and is never written down, and when the table is full it keeps only the addresses at their cap, so new ones still get in. The address is the connecting one, or `CF-Connecting-IP` with `--trusted-proxy cloudflare`: behind any other proxy every install shares the proxy's address, so the cap holds them all to 200 a day together. Unvetted counts take at most 1 000 000 rows a day, a valve for the disk rather than a limit any real day reaches. Past any of these, a batch is answered like any other and dropped.
- **Reading them.** `admin signals` lists the last 7 days, newest first, `--days <n>` another span, `--json` as JSON; each line is the day, the count, the component and kind, the build, the OS and architecture, and `unvetted` for counts from keys not allowed.

Counts are deleted 180 days after their day.

## Commands

A device answers a question, approves a push, starts a task or runs a routine by sending a command: an envelope of kind `answer`, `push`, `start` or `routine`, sealed to the machine (and to the device itself), signed with the device's key. The hub carries it and cannot read it; the machine decides.

The hub checks what it can without the content, and queues nothing that fails:

- the device token, and that the header is well formed with an id, sender and lifetime that fit a command (at most 24 hours);
- that `from` is the device sending it (`400 wrong-sender`) and `kind` is a command kind (`400 not-a-command`);
- that the machine named in the header admitted the device (`404 unknown-machine`, the same for a machine that does not exist);
- that the key rows are for that machine and at most the device itself (`400 bad-recipients`);
- the signature, against the keys the device was admitted with (`400 bad-signature`), and that it has not expired (`400 expired`) or been signed more than 5 minutes ahead (`400 not-yet-valid`);
- sizes: a request of at most 64 KiB, a ciphertext of at most 36 KiB for `answer` and `start` and 4 KiB for `push` and `routine` (`413 too-large`), at most 1000 envelopes waiting in a machine's queue and at most 100 undelivered commands from one device to one machine (`429 queue-full`);
- a rate per device and kind: 30 at once and 30 a minute for `answer` and `routine`, 5 at once and 5 a minute for `start` and `push` (`429 rate-limited`), on top of the per-token limit every call has.

The machine applies a command with `authorize` from the protocol crate. It drops, without a reply, anything that fails before the signature checks out against its own list of trusted devices. It answers a command it applied before with the stored result. Otherwise it refuses, with a result the device can show, a command that expired while it waited in the queue (`expired`), one from a device with the `read` role or of a kind the machine does not take (`not-allowed`), and one that does not decrypt or is not well formed. Only then does the machine act: a push goes through only if the task's HEAD is still the sha the device signed (`head-moved` otherwise), and in kebbie an answer to a question that no longer waits is `already-settled`.

The hub drops a queued envelope once its `exp` has passed, so a machine that slept through the window comes back to an empty queue. Removing a device, by its account or by a machine, drops its commands that machine has not been handed yet.

The result is an envelope of kind `result` under the command's id, sealed to the device that sent the command. The hub stores it only for a command it delivered to that machine from that device, and announces it on the device's feed by id.

A pairing moves `open → committed → replied → revealed → admitted`, or ends `refused`, `failed` (a second commitment to the same code) or `expired`. Each step is accepted once; anything out of order is `409`. A device's public keys are fixed by its first admission, not by a reveal, so a relay that swaps keys in a refused pairing cannot lock the device out.

Requests are rate limited per token or account (commands also per device and kind, above), and per client address (IPv6 per /64) for unauthenticated calls and bad credentials; an address that has used up its bucket is refused before any lookup. The limiter keeps at most 100 000 buckets. Numbers above `i64::MAX` (`rev`, `after`) get `400`. Bodies are capped at 16 KiB, boards at 1 MiB. A connection that has not sent its request headers within 10 seconds is closed, and a request body that sends nothing for 30 seconds is cut. The hub serves at most 4096 connections at once; further ones wait to be accepted. A device holds at most 8 event feeds at once, and a ninth gets `429 too-many-feeds`. Long-polls and feeds end when the hub shuts down. The hub sends no CORS headers, so the web app is served from the hub's own origin.

Long-polls and event feeds wake only for their own machine, pairing or device.

## Notices and Web Push

A machine tells its devices that something needs them with a notice: an envelope of kind `notice`, sealed to the devices it paired with and signed by the machine. Its header carries `urgency` (`high` for a question, needs-you or a failed CI, otherwise `normal`) and `collapse`, an opaque tag per task, both covered by the signature. The content (`title`, `body`, the question and its options, `retract`) is end to end encrypted like a board.

`POST /v1/m/notices` checks, before anything is pushed:

- that the envelope is a notice (`400 not-a-notice`) for this machine (`400 wrong-machine`), signed by it (`400 bad-signature`), unexpired (`400 expired`) and well formed;
- that its key rows are devices, and at least one (`400 bad-recipients`);
- that each device's cut of the envelope fits one push (`413 too-large`): at most 3993 bytes of envelope JSON, so the encrypted push body stays within the 4096 bytes every push service takes;
- a rate of 30 at once and 30 a minute per machine (`429 rate-limited`), and that the notice id is new (`409 replayed-envelope`).

The hub then pushes to every recipient device that the machine still admits and that has a subscription, at most 30 at once and 30 a minute per device across all machines (a push over that is dropped and logged `push.capped`). The response does not wait for the push services: deliveries run in the background, at most 4096 waiting or retrying and at most 256 requests open at once. A request slot is held only while a request is out, never through a retry's wait, so a failing push service does not hold up the others. A delivery that finds the 4096 taken is dropped and logged. Each delivery checks its endpoint against the known push services and `--push-allow-host` again before sending, so a host dropped from the allowlist gets nothing (`push.refused`). Redirects are not followed.

Each push is the envelope cut to that device's key row, as JSON, encrypted to the subscription's keys with `aes128gcm` (RFC 8291) and sent with:

- `Authorization: vapid t=<JWT>, k=<public key>` (RFC 8292): an ES256 token with `aud` the endpoint's origin, `sub` the `--vapid-subject`, `exp` 12 hours out;
- `TTL`: the seconds left until the envelope's `exp`;
- `Urgency`: the header's urgency;
- `Topic`: the collapse tag when it is 32 characters or fewer, otherwise the first 32 characters of the base64url SHA-256 of it, so a newer notice for the same task replaces an undelivered one at the push service.

How the hub reads the push service's answer: `201` or any other 2xx is delivered; `404` and `410` mean the subscription is gone, and the hub deletes it (iOS hands out a new endpoint whenever the service worker registers again); `413` is logged; `429`, a 5xx or no answer is retried 3 times, waiting 1, 2 and 4 seconds or the `Retry-After` it names (at most a minute), and then dropped; any other status, a redirect included, is logged as `push.refused`, and a `401` or `403` is also printed, since it usually means the VAPID subject or key is wrong. The hub keeps no notice content, so a notice that found no subscription, or whose push was dropped, is gone; the device sees what it was about on the board.

**What a push service sees.** Apple, Google, Mozilla or Microsoft see the hub's address, its VAPID public key and subject, the endpoint, when each push is sent and how large it is, its TTL, urgency and topic. The body is encrypted to the browser's subscription key; inside it is the sealed envelope, which only the device can open. The topic is a hash of an opaque tag, so it groups one task's notices without naming the task. The hub itself sees the same as for a board: which machine notified which devices, when, how urgently and how large, never the text.

iOS does not replace a shown notification that has the same `tag`, so a notice is never quietly withdrawn: when a question is settled elsewhere, the machine sends a new notice whose sealed `retract` names the collapse tag, and the service worker closes the old notification.

## What the hub stores

One sqlite file: machine ids, names, public keys and the account each belongs to; accounts (id, handle, a random WebAuthn user handle, creation time, role, plan status and its end, when it was deactivated, a verified email and when it was verified, the id and login of a linked GitHub user, and the kind of ticket it was made with: `setup`, `invite` or `connect`); pending connects for 10 minutes (SHA-256 hashes of the device code and the user code, the machine's proposed name and public keys, the approving account and the machine and pairing the approval made, the poll interval and the last poll); each passkey's public key, signature counter, name and use times; SHA-256 hashes of machine, device and session tokens, never the tokens; SHA-256 hashes of join codes, invites, the setup token, email verification tokens (with the address they verify) and pairing codes, so they cannot be read off the file, though a code's 40 bits do not resist offline guessing during its life; pending passkey ceremonies and GitHub sign-ins (the state's SHA-256 hash, the PKCE verifier, a SHA-256 hash of the browser's state cookie, the path to return to and the ticket's hash) for 5 minutes; each passkey's PRF salt; each account's public keys with their version, each passkey's wrapper of the private keys (which the hub cannot open without the passkey), and each account's newest signed machine list; device ids, names, public keys and owning account, and which machine admitted each device; the latest board envelope per machine, as ciphertext with its key rows, its id and signed time; account key handoffs as pairings, with the commitment and the revealed public keys; queued envelopes until acknowledged or expired; for each command, the sending device, the machine, the id, the kind, a SHA-256 of the envelope (to recognise a resend), its queue position and when it was queued and delivered, kept 7 days; results, as ciphertext with their key rows, until they expire (at most 7 days); pairing sessions, deleted an hour after they expire; each device's push subscription (the endpoint and the browser's public `p256dh` key and `auth` secret, which let the hub encrypt to the browser but not decrypt); the ids of posted notices until they expire, to refuse a replay; error reports (title, text, version and OS as sent, the sender's public key, arrival and acknowledgement times) and each key's standing (quarantine, allowed or blocked) with when it was first and last seen; error signal counts per day, version, commit, OS, architecture, component, kind and whether the sender was vetted, for 180 days, and each sender key's number of signal batches today, until the day turns; the nonces of spent report challenges until they expire; SHA-256 hashes of admin tokens with their names, scopes and when each was made and last used; and an event log of what happened when (joins, stored revisions and sizes, pairing steps and refusal reasons, connects started, approved and denied, sign-ups and how, GitHub links and removals, owner changes from the CLI, sign-up mails sent (never the address), plan changes, deactivations, logins, device registrations and removals, queued commands with their kind and size, stored results, push subscriptions with the push service's host, posted notices with their size and number of pushes, each push's outcome with the push service's status, each report's id, outcome and size, never its text, and each signal batch's outcome and number of counts, never its key), kept 30 days.

Every minute the hub sweeps expired sessions, ceremonies, invites, connects (with the machine an unredeemed approval made) and codes, and devices that no account holds and no machine admits once none of their pairings is still open. A database written by schema 9 gains the column for the ticket each account was made with at start-up, one written by schema 8 the GitHub login column too, one written by schema 7 the account key tables, a PRF salt for every passkey it holds and the new columns at start-up, one written by schema 6 the connect table too, one written by schema 5 the signal tables as well, and one written by schema 4 the report tables; one written by an earlier schema is refused.

Apart from error reports, which are plain text by design, and error signals, which are counts, it never stores or sees a board's, command's, result's or notice's content, a machine's, device's or account's private key in the open, a PRF output, or a token. Its own VAPID private key is in its key file, outside the database. It cannot decrypt an envelope, and it does not decide which devices a machine trusts: it records the machine's decision.

## Not yet

- Answering, pushing and starting tasks from the web app: the buttons are there, disabled. Commands will be signed by the account's signing key.
- Notifications in the web app: notices are sealed to devices, and the web app registers none, so its service worker shows only "Something on the board changed." Push subscriptions signed by the account key come next.
- Unlocking on a device whose passkey gives no PRF output, and rotating the account key.
- The bridge in kebbie that applies commands and posts notices for real, the collapse key a machine shares with its devices at pairing, and kebbie's side of the account key handoff.
- APNs for an iOS app.
- OIDC sign-in for self-hosted hubs.
- Billing itself: the open hub only records each account's plan.
- Removing an account.
- Logging out everywhere, and ending an account's sessions when one of its passkeys is removed.
- An event to an open feed when `admin remove-machine` runs: the CLI is another process, so a connected device learns of it on its next request.
